# Account lifecycle implementation evidence

Local implementation on the approved isolated beta branch; no production changes or real email/storage calls were made.

- The account API follows the approved design. Reset/verification tokens are random, stored only as SHA-256 digests, expire by PostgreSQL time, and are consumed once under an account lock. Sending a replacement invalidates earlier links of that purpose. Password reset invalidates all prior sessions and outstanding account links.
- JWTs carry a unique identifier and account generation. Legacy generation-zero tokens work until the account is revoked. Ordinary logout persists a token digest revocation; logout everywhere increments the account generation. Password-confirmed deletion returns 403 for a wrong password and atomically removes the account and FK-owned data. Monetary AI ledgers/reservations remain intact for reconciliation and the global cap.
- Configure `EMAIL_PROVIDER=ses`, `SES_REGION`, `SES_SENDER_EMAIL`, `SES_IDENTITY_VERIFIED=true`, and `PUBLIC_WEB_ORIGIN` only after verifying the SES sender and sending access. The origin must exactly match a configured CORS origin, with HTTPS in production. The adapter uses SES v2 `SendEmail` through the task role; grant `ses:SendEmail` for the chosen sender. Missing setup gives capabilities=false and the same 503 for known/unknown accounts. Delivery exceptions give the same accepted public response and a secret-free log event. Tokens exist only in an in-memory post-response delivery task; a process crash before delivery requires requesting another link.
- New uploads reserve exact storage coordinates and ownership durably before writing. Deletion queues objects and a minimal counter-cleanup tombstone in the same transaction. Pending uploads have a five-minute settling window. The API lifespan starts a bounded, cross-replica-safe cleanup poller; `ACCOUNT_CLEANUP_ENABLED` and `ACCOUNT_CLEANUP_POLL_SECONDS` control it. S3 cleanup requires `s3:DeleteObject` for the configured recipe prefix. Failed/unknown cleanup is retried with durable leases and backoff.
- Cleanup preserves recipe and cooking-snapshot references, including copied URLs with query/fragment suffixes and relative/local-host aliases. Database guards serialize new image references with deletion admission; a late copy retains its recipe and loses an image already being deleted. Arbitrary URLs, foreign-account paths, mismatched buckets, and local symlinks are never deletion targets. Older S3 paths are adopted only when configured-bucket/account ownership is provable. Older local uploads lack ownership records and are retained for a separate inventory. Shared copies, backup retention, and minimal pseudonymous accounting/cleanup records are outside immediate account-row deletion.
- Final focused validation: 59 tests passed using disposable PostgreSQL `chef_beta_accounts_20260922`, including token replay/concurrent consumption, legacy revocation, reset/deletion races, request limits, pending upload/deletion races, copied references, storage retries, origin validation, secret-free delivery failures, and existing auth/storage/lifespan regressions. The finalized migration was downgraded/upgraded successfully on that disposable DB only.
- A broader backend run excluding the mismatched video dependency had 538 passed and 66 skipped; 16 synthetic Chromium tests initially hit sandbox process restrictions and then all passed with local browser access. The supplied venv had youtube-transcript-api 0.6.3 while this source pins 1.2.4; the root worker prepared a separate matching dependency directory for final full-suite validation.


Independent review fixes: recurring counter sweeps retain only the deleted UUID's scopes, so re-registering the same email keeps the new account's admission counters. A late upload completion cannot reopen image reference admission after cleanup has started; it invalidates the earlier lease and queues another idempotent cleanup. Both PostgreSQL regressions failed before the fixes and passed afterward.
