# Chef World data inventory

Code review date: September 22, 2026. This describes the local beta implementation, not deployed behavior. Cloud retention settings, provider contracts and live email/storage access require separate verification before publishing a privacy policy or App Store declarations. See the [beta release handoff](qa/2026-09-22-beta-readiness-implementation.md) and [account lifecycle evidence](qa/2026-09-22-account-lifecycle-implementation.md).

| Data | Purpose and storage | External disclosure or visibility | Current lifecycle |
| --- | --- | --- | --- |
| Account UUID, email, verification status, library visibility | PostgreSQL `users`; authentication, session generation and optional sharing | Authenticated email lookup can return a public-library account; configured SES receives recipient email for requested account links | Password-confirmed in-app deletion removes the account and owned relational data. Recovery/verification are implemented but real SES setup is pending; email change is not implemented |
| Password hash | Bcrypt hash in `auth_identities`; submitted password is used for authentication/reset/deletion confirmation | No intended provider disclosure; validation excludes submitted values | Successful reset replaces the hash and revokes prior sessions/links. Account deletion cascades the identity row |
| Authentication token | Seven-day JWT with token ID/account generation; HttpOnly web cookie or native SecureStore. Revoked-token digests/expiry in PostgreSQL | Sent only to the configured application API | Logout revokes the presented token; logout-all/reset revoke earlier account generations. Deletion removes the account. Expired revocation records are pruned by cleanup. Client state clears after successful actions or confirmed expiry |
| Recovery/verification links | Random raw token only in response-delivery/client memory; SHA-256 digest, purpose and expiry in `account_action_tokens` | Configured SES receives the token link and recipient email; browser uses a first-party URL fragment then removes it | Single-use, database-clock expiry; replacement/reset invalidates earlier links; expiry cleanup/account deletion removes rows. No raw token persistence or logging intended. Delivery is not durable; provider mail retention remains unverified |
| Import text and guidance | Extraction input; saved as `raw_extraction_text` only when the reviewed import is saved | Sent to OpenAI for explicit extraction; shared projections/new cross-account copies omit it. Manual entry saves without a provider call | Owned text follows recipe/account deletion; historical copied text needs an explicit data review |
| Public video URL and description | Text retrieval before recipe extraction | YouTube/TikTok receive requests for the selected public video; the retained YouTube fallback can send its canonical public URL to Jina Reader when direct text access fails | No account email, private guidance or API credential is included in that Reader request; external service retention and availability require provider review |
| Recipe title, ingredients, steps, tags, source and image URLs | Owned PostgreSQL recipes, entered manually or saved after import review | Enabled friend sharing/editor catalog can expose recipe details; copies are separate owned records | Recipe/account deletion removes owned recipe rows, not other users' copies/snapshots. Ordinary recipe deletion does not run an image orphan sweep; account-owned image cleanup follows the rules below |
| Grocery ingredients and tutorial text | Deterministic grocery aggregation; optional on-demand refinement/timing estimates | Basic groceries/check/copy/share require no AI. Explicit refinement/estimation sends relevant text to OpenAI; user-selected share destinations receive shared text | Saved data/caches follow their own lifecycles; provider/share-destination retention needs verification. AI failure leaves the basic list usable |
| Uploaded images | API-validated bytes in S3/local storage; durable `owned_images` coordinates, owner UUID, state, lease and retry metadata reserved before upload | Image URLs work independently of recipe authorization; actual bucket policy is unverified | Account deletion queues owned unreferenced objects after settling; failed/unknown deletes retry. Recipe/cooking-copy references defer deletion. Late uploads preserve deletion admission and requeue cleanup. Provably owned legacy S3 keys may be adopted; unowned legacy local images require inventory. Ownership receipts survive deletion; no fixed receipt retention cutoff is implemented |
| Meal plans | Per-account/date recipe references in PostgreSQL; client fingerprints | Application API aggregates grocery needs | Account deletion cascades plans and clears private client state. No ordinary historical meal-plan expiry |
| Active cooking session, actions and device identifiers | PostgreSQL snapshot, revisions and mutation IDs; device cache/offline queue | Synced across authenticated devices; local notifications use device identifiers | Finish/discard/account deletion removes owned session children. Recipe deletion preserves an active cook. Other users' copied snapshots survive source-account deletion; logout/account change clears owned device state/alerts |
| AI request/upload/abuse counters | PostgreSQL global/account operation windows, upload reservations, HMAC address/IP/UUID request scopes | No recipe text or credentials in counters | Deletion removes non-monetary account counters. Email-derived scopes are removed once at deletion; a UUID-only tombstone periodically removes late account-scoped writes without clearing a new account's reused-email allowance. Global counters remain |
| AI monetary budgets and call ledger | PostgreSQL global/account monthly spent/reserved amounts, account UUID, model/price version, usage and call outcome | Admin-only operational reporting; no recipe text or credentials | Intentionally retained after account deletion for unknown-call reconciliation and the global USD 30 modeled app cap. Unknown costs remain reserved; deletion/recreation never refunds spend. No fixed monetary-ledger retention cutoff is implemented |
| Deletion tombstones | `deleted_accounts`: former account UUID, UUID-derived request scopes and next sweep time | Operational cleanup only; not publicly exposed | Retained to clean late non-monetary counter writes; no email retained in tombstones and no fixed expiry implemented. Separate retention policy needed |
| Retail search queries/results and HTTP leases | Weee service, shared PostgreSQL/in-process cache; temporary request UUID/account UUID/expiry leases | Ingredient searches go to Weee; opening product links sends normal browser/device requests | Product freshness is 24 hours, not a physical cache-row deletion promise. Replica-shared request limits/expiring leases bound admission; lease expiry is independent of persistent scraper-job completion |
| Instacart export title and selected items | Stateless authenticated API request; returned link held in client memory | Title, item names, display quantities and recognized measurements go to the configured Instacart API | Implementation requests a seven-day link; provider-side retention and permitted production access still require verification |
| Shopping selections and checked items | Smart selections/checks use account-scoped web storage or native ephemeral storage; basic checks stay in screen state | Explicit retailer links or user-selected copy/share; no inferred checkout/cart completion | Account changes/successful logout invalidate private state; cooking offline data is separately account-keyed. Basic checks do not create a persistent grocery history |
| Language, display and notification preferences | Device/browser preferences | No intended provider disclosure in these preference handlers | Preserved across logout as device preferences |
| Application and infrastructure logs | Operation diagnosis, status, timings and error types | Hosting/operator access depends on deployed configuration | Uvicorn access logs now omit query strings; AI logs omit prompts/provider bodies. Retail-service diagnostics still include search terms. Proxy/CDN logs, access controls and retention need independent review |

## Decisions required before release

1. Assign a business owner to each hosting, database, storage, AI, retail and Apple developer account. Record service identities, access reviews, incident contacts and billing ownership without copying credentials into this repository.
2. Define retention for backups, shared/copied content, provider-held state, logs, legacy unowned images, ownership receipts, UUID tombstones and retained AI monetary records. Implemented account deletion/cleanup does not promise immediate removal from these locations.
3. Verify the implemented in-app deletion and leased image cleanup on the actual release/storage setup, including task permissions, retries and late uploads. Explain that library visibility changes/deletion do not recall other users' copies; retain those references safely. Verify recovery/verification with a real configured sender before advertising delivery.
4. Review what recipe sharing communicates to users. Original import guidance is now private in shared projections and new copies, but historical copied text may already exist. Decide on any notice/backfill using actual data and ownership evidence.
5. Verify provider data terms and cloud settings, then publish an accurate privacy policy/support contact and complete the App Store privacy questionnaire. Do not infer a provider's retention or training settings from the API code.

Apple release references (recheck before submission): [in-app account deletion](https://developer.apple.com/support/offering-account-deletion-in-your-app/) and [App Privacy Details](https://developer.apple.com/app-store/app-privacy-details/).
