# Chef World data inventory

Code review date: September 14, 2026. This describes the reviewed local implementation. Cloud retention settings, provider contracts and deployed configuration require separate verification before publishing a privacy policy or submitting App Store declarations.

| Data | Purpose and storage | External disclosure or visibility | Current lifecycle |
| --- | --- | --- | --- |
| Account UUID, email, library visibility | PostgreSQL `users`; authentication and optional sharing | Authenticated email lookup can return an account whose library is public | No in-app account deletion or email-change/recovery flow |
| Password hash | Bcrypt hash in `auth_identities`; original password is used only for authentication | No intended provider disclosure; request validation excludes submitted values | Account-linked row has a cascading foreign key, but an account deletion workflow is not implemented |
| Authentication token | Seven-day JWT; HttpOnly web cookie or native SecureStore | Sent only to the configured application API | Logout clears client state/cookie; issued bearer tokens have no central revocation mechanism |
| Import text and guidance | Sent for extraction, then retained as `raw_extraction_text` if the reviewed recipe is saved | Sent to OpenAI for extraction; current shared projections and new cross-account copies omit it | Owners retain their original text; existing historical copies need an explicit data review |
| Public video URL and description | Text retrieval before recipe extraction | YouTube/TikTok receive requests for the selected public video; the retained YouTube fallback can send its canonical public URL to Jina Reader when direct text access fails | No account email, private guidance or API credential is included in that Reader request; external service retention and availability require provider review |
| Recipe title, ingredients, steps, tags, source and image URLs | Owned PostgreSQL recipe records | Recipe details are exposed through enabled friend sharing or editor-published catalog entries; a copy becomes a separate owned record | Recipe deletion removes the recipe row, but does not remove separately copied recipes, cooking snapshots or image objects |
| Grocery ingredients and tutorial text | On-demand refinement or timing estimates | Sent to OpenAI when the user requests that operation | Client caches and saved recipe data follow their respective lifecycles; provider retention must be verified |
| Uploaded images | API-validated bytes in S3 or local uploads directory; URLs stored with recipes | Image URLs are usable independently of recipe authorization; actual S3/bucket policies are not verified here | No image deletion/orphan cleanup job; new S3 keys include account ID, historical keys do not consistently establish ownership |
| Meal plans | Per-account/date recipe references in PostgreSQL; client fingerprints | Used by the application API to aggregate grocery needs | No explicit historical meal-plan expiry; account-linked rows have cascading foreign keys |
| Active cooking session, actions and device identifiers | PostgreSQL snapshot, step revisions and mutation IDs; device cache/offline queue | Synced between authenticated devices; local notification scheduling uses device identifiers | Finishing/discarding removes the active session and children; original recipe deletion intentionally does not destroy an active cook |
| AI allowance counters | PostgreSQL account/global window counters | No recipe text or credential stored in counters; operational model logs include token counts and request metadata | Windows reset logically; account-scoped counter rows need explicit removal in future account deletion because they do not have a user foreign key |
| Retail search queries/results | Weee search service, shared PostgreSQL cache and in-process cache | Ingredient search terms go to Weee; opening product pages exposes the normal browser/device request to the retailer | Product freshness is 24 hours; freshness expiry is not a guarantee that the database row is physically deleted |
| Instacart export title and selected items | Stateless authenticated API request; returned link held in client memory | Title, item names, display quantities and recognized measurements go to the configured Instacart API | Implementation requests a seven-day link; provider-side retention and permitted production access still require verification |
| Shopping selections and checked items | Web account-scoped browser storage; native in-memory shopping storage | Retail handoff opens explicitly selected links; it does not establish checkout or cart completion | Account changes/logout invalidate state; cooking offline data is separately account-keyed |
| Language, display and notification preferences | Device/browser preferences | No intended provider disclosure in these preference handlers | Preserved across logout as device preferences |
| Application and infrastructure logs | Operation diagnosis, status, timings and error types | Hosting/operator access depends on deployed configuration | Uvicorn access logs now omit query strings; AI logs omit prompts/provider bodies. Retail-service diagnostics still include search terms. Proxy/CDN logs, access controls and retention need independent review |

## Decisions required before release

1. Assign a business owner to each hosting, database, storage, AI, retail and Apple developer account. Record service identities, access reviews, incident contacts and billing ownership without copying credentials into this repository.
2. Define retention and deletion for account data, backups, uploaded images, logs, AI counters, shared/copied content and provider-held state. Foreign-key cascades alone are not a complete account deletion implementation.
3. Implement and test in-app deletion, including an explicit explanation of how already-shared content is handled. The existing share toggle affects future library visibility; it does not recall copies already made by another account.
4. Review what recipe sharing communicates to users. Original import guidance is now private in shared projections and new copies, but historical copied text may already exist. Decide on any notice/backfill using actual data and ownership evidence.
5. Verify provider data terms and cloud settings, then publish an accurate privacy policy/support contact and complete the App Store privacy questionnaire. Do not infer a provider's retention or training settings from the API code.
